# Security Boundary

Baseline review date: 2026-10-04. Latest contract review: 2026-10-08. This document was last updated on 2026-11-05. Scope of that review: local synthetic console plus the PayPal Sandbox adapter. Later additions (the country rules check, the evidence guide's optional Gemini chooser, AG Studio's built-in agents and their Gemini route, the Channel3 category signal, product reference card and case routing, the hosted demo (no PayPal calls; opt-in Gemini guide), its traffic layer, the console's session resume through sessionStorage, Sandbox dispute reads, gated Sandbox evidence submission and gated Sandbox shipment tracking) are described below and in README.md; they were not part of that review.

Backend route/auth/data controls are specified in docs/decisions/2026Q4/console_contract.md. Loopback binding, exact Origin/Host allowlists, session-bound CSRF, memory TTL and row/rate/body bounds are required for the local console. The hosted demo container binds `0.0.0.0` on `$PORT` behind Render's proxy; there the backend accepts a non-loopback client only when it names the one configured `PAYGUARD_PUBLIC_HOST` and carries the proxy's `X-Forwarded-For` and `X-Forwarded-Proto: https` headers, and a per-visitor and store-wide traffic layer applies (`backend/app/traffic.py`; limits in README "Hosted demo"). The only public deployment is the optional hosted demo (`PAYGUARD_DEMO_MODE=public`, README "Hosted demo", `https://payguard-demo-j2b3.onrender.com`). It makes no PayPal calls and holds no PayPal or Google Cloud credential. Its one model path is opt-in: when the operator sets `PAYGUARD_HOSTED_GUIDE_MODEL=gemini` and stores a free-tier Gemini key as a Render secret, the evidence guide's clause chooser may call Gemini, at most 5 calls a minute and 20 a day across all visitors (guide only; without the opt-in it stays on the keyword chooser). Every other provider-reaching route (`POST` Sandbox connect, invoice draft, provide-evidence, add-tracking, webhook verification, AI brief and the AG Studio agent turn) answers 503 `hosted_demo_disabled`. The Channel3 category signal is forced off there and the product reference card replays recorded searches, so the backend makes no Channel3 call; the recorded cards' images are loaded by the visitor's browser from `cdn.trychannel3.com`. The read-only `GET` PayPal routes stay available there and answer from the synthetic Disputes fixture (`GET /api/v1/paypal/status` and `GET /api/v1/paypal/disputes` answer 200; `GET /api/v1/paypal/disputes/{id}` for an unknown id answers 404); none of them calls PayPal. A hosted deployment with provider calls, and real merchant authentication, are not claimed.

Secret owner: the local operator owns PAYPAL_CLIENT_ID and PAYPAL_CLIENT_SECRET. Storage: backend process environment only; agents must not inspect values or read .env files. The backend reads no .env file. The frontend build reads `frontend/.env.local`, if present, only for the optional AG Studio licence key; that key is compiled into the dashboard page, so anyone who loads a build made with it can read it. Rotation: replace Sandbox app credentials through the PayPal developer dashboard, restart the backend to invalidate cached access, and verify only the sanitized connection status. Revoke: disable the Sandbox app credentials through the provider and stop the local adapter. No provider credentials or upstream payloads enter logs, receipts, browser state or exports. The demo session id and its CSRF token are a different matter: to resume the session after a reload, Back or the dashboard link, the console keeps them, together with the seller's own product description and the selected case reference, in this tab's sessionStorage until the tab closes (`frontend/src/App.jsx`). Script running in that origin can read them. This is an accepted deviation from OWASP session-management guidance, which advises against keeping session identifiers in web storage, made because the demo has no accounts, holds only synthetic data and the session expires on the server; it would not be acceptable for real merchant sessions.

HMAC identifiers are pseudonymization. Local review is not durable authenticated authorization. No invoice send, payment, refund or production dispute submission is enabled. Sandbox dispute evidence submission is a separate opt-in (`PAYGUARD_PAYPAL_DISPUTE_SUBMIT=enabled`) and also needs a Sandbox connection, a recorded local approval and an explicit `submit: true`. The server also issues a single-use send confirmation with each preview, bound to the session, dispute, case, payload hash and review gate, valid only after 3 seconds and consumed under the store lock; a send without it is refused (409) before any PayPal call. As of 2026-10-31 no evidence had been sent to Sandbox; on 2026-11-04 one evidence send to an author-created Sandbox test dispute succeeded ([masked receipt](docs/evidence/RECEIPT_20261104_live.md)); on 2026-11-05 (UTC+8) a second send to a newly filed Sandbox test dispute succeeded ([masked receipt](docs/evidence/RECEIPT_20261105_live.md)). Sandbox shipment tracking (`POST /v1/shipping/trackers-batch`, which PayPal marks deprecated (legacy); Orders v2 tracking, `POST /v2/checkout/orders/{id}/track`, is the current path and is not called) is gated the same way by its own opt-in (`PAYGUARD_PAYPAL_TRACKING_SUBMIT=enabled`), the recorded local approval and `submit: true`; no tracking request has been sent live. Sandbox dispute list and detail reads (`GET`) run when a Sandbox app is connected. The bounded AI path is disabled by default. The Python 3.13 API imports no provider SDK; a dedicated Python 3.12 worker owns `google-genai==2.28.0`. For the evidence brief it may send only the stage, closed facts that the server computes from the session's synthetic records (for an optional `case-ref-NNN` reference; the caller cannot supply fact values) and pinned citation IDs to Vertex API `v1`, location `global`, model `gemini-3.8-flash`, and the brief accepts no raw PII, caller-supplied merchant payload, arbitrary prompt, tool call or financial action. The evidence guide's Gemini chooser (`PAYGUARD_GUIDE_MODEL=gemini`, off by default) uses the same worker but sends up to three sanitised seller sentences (ASCII, bounded length) and the form's item ids, over Vertex AI or, with `PAYGUARD_GEMINI_TRANSPORT=api_key`, the Gemini API with an AI Studio key (`GEMINI_API_KEY`) that is passed only to the worker's clean environment. The guide has its own caps: 10 model calls per session and situation (up to 30 per session across the three situations), 2 seconds between calls, a daily limit, 30 calls a minute, an in-flight limit and a failure breaker, all counted in the guide's own process-local counter. AG Studio's built-in agents (`PAYGUARD_STUDIO_AGENTS=gemini`, off by default and never built on the hosted demo) use the same worker and either transport: `POST /api/v1/studio/agent-turn` forwards Studio's instructions, the operator's question (600 characters at most, refused if it looks like an email address or a phone or card number), tool schemas and tool results over the synthetic dashboard data, with closed input and bounded output checked in the backend and the worker. That route has its own separate counter: 20 calls per session, 0.5 seconds apart, a per-client and a global daily limit, 30 calls a minute, an in-flight limit and a failure breaker. The Channel3 category signal and product search (`PAYGUARD_CHANNEL3=enabled` with `CHANNEL3_API_KEY`, off by default) send only a sanitised product name to `api.trychannel3.com`, with the key in a request header only, a hard timeout, no redirects, no retry, a bounded body and process-local ceilings of 20 calls each; case routing may spend at most 8 live product searches per process and 2 per session, and only when its local match finds no goods group. The server-owned `payguard-bounded-advisory-v3` prompt contract treats all input as data, disables tools and automatic function calling, and constrains every generated sentence to a stage-specific enum. Disabled or invalidly configured AI requests fail before reservation. After enablement and deterministic context validation, the backend permanently reserves a maximum of three brief attempts per process, one per fixed stage, before provider execution. Failed, timed-out, cancelled and invalid-response attempts consume their slot; no automatic retry occurs. Session reset, expiry or replacement cannot restore a slot. Process restart and multiple workers can still create new local budgets, so any public multi-instance deployment requires a durable shared atomic quota and an API-gateway cost circuit breaker before outbound AI is enabled. The operator-attested reviewed receipt records one observed invocation only; public source, mock transport results and the receipt cannot establish repeatability, real-record safety, policy correctness or production readiness.

The optional LM Studio profile is a separate default-off loopback transport. It is fixed to `127.0.0.1:1234` and `nvidia-nemotron-3-nano-4b`, uses `httpx` with `trust_env=False` and redirects disabled, sends no authentication header, accepts no endpoint or model override, serializes inference, requests no reasoning, exposes no tools and never falls back to Gemini. Nonempty reasoning, tool calls, model drift, extra generated fields, free text, reordered citations and invalid authority fields fail closed. Starting the local profile does not authorize network exposure; LM Studio must keep local-network serving disabled.

## Public upload credential prohibition

Repository content, release packages, browser bundles, screenshots, logs and AI prompts must contain no credential value, access token, provider project identity, account identifier or `.env` payload. Configuration names may be documented only as names. Operator credentials remain outside Git in the backend process environment or an approved deployment secret manager. Public packaging must run the exact secret, history and export gates against the candidate bytes; a passing scan does not authorize publication.

Threat model: docs/decisions/2026Q4/threat_model.md. Package review and locked dependency evidence are recorded in the console work-order manifest. Release state is determined by the package manifest and exact anonymous public readback, not by this document or a historical receipt. When the manifest is `PUBLIC_SOURCE_PUBLISHED` with `publication_authorized=true` and the same bytes pass exact anonymous readback, public source publication is complete. The committed manifest describes the bytes of the build it shipped with (its `created_at_utc`); later working-tree revisions are not covered by it until a fresh build and review. In that published-source state, the Devpost project is submitted; the 2:02 demonstration is already public. A package marked `LOCAL_EXPORT_CANDIDATE_REVIEW_REQUIRED` has not crossed the public-source gate. Historical operator-attested Sandbox and Gemini receipts prove only their captured executions and do not establish current-byte live provider behavior. Apart from the hosted demo above, deployment approval remains open; this evidence does not authorize production hosting, a hosted deployment with provider calls, production PayPal authority, real PII, shared quotas or local-model distribution.
