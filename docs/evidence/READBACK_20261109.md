The two PDFs differ from each other (their dates are counted from the moment each draft was prepared), which is why each send has its own fingerprint.

## What went wrong first, and what it was
The first read-backs (both disputes) answered HTTP 404 for the document. The cause was the read-back tool: it asked PayPal's content service (`/v2/content/documents/<token>/files/1/download`) for `Accept: application/json`. The same request with `Accept: application/pdf` returns the file. `tools/sandbox_readback_hash.py` now asks for the PDF first, and a test covers it.

## What this does and does not show
- It shows that, for sends 2 and 3, the file PayPal's Sandbox serves back is byte for byte the file TradeGlot sent, and that each fingerprint was taken at the moment of sending.
- It does not cover send 1 (no fingerprint had been recorded then), and it does not mean PayPal accepted the evidence or will decide in the seller's favour; PayPal decides every outcome.
- The generated PDF carries dates counted from the moment the draft is prepared, so a send cannot be rebuilt byte for byte afterwards. That is why the fingerprint is recorded at send time.
