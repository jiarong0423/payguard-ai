# Sandbox read-back after a send with the generated PDF, 2026-11-09

Sandbox test data created by the author. One of three author-created Sandbox "item not received" test disputes was answered from the local console after one human approval (two presses on "Submit to PayPal Sandbox"). The file sent was the generated delivery PDF (`synthetic-delivery.pdf`, 2,015 bytes in the console's preview), not the 43-byte placeholder of the earlier sends. The dispute id is masked here.

The read-back is read-only (one token request, one dispute read, one document request) and was run in the author's own terminal with the author's Sandbox keys:

| Field | Value |
| --- | --- |
| dispute | PP-R-BN... (masked) |
| status | WAITING_FOR_BUYER_RESPONSE |
| stage | INQUIRY |
| seller evidence entries | 1, type PROOF_OF_FULFILLMENT |
| seller documents listed by PayPal | 1, named `synthetic-delivery.pdf` |
| document download | HTTP 404 |

What this supports: PayPal's record shows the seller's evidence, the file name and the changed dispute status.

What it does not support:
- It does not show that the bytes PayPal holds equal the bytes sent. The document request answered 404, so nothing was compared.
- The generated PDF carries dates counted back from the moment the draft is prepared, so the same case gives different bytes each time. The send-time fingerprint was only shown on screen and was not kept, and an offline rebuild gave a different hash. A later check by hash is therefore not possible for this send.
- It does not mean PayPal accepted the evidence; PayPal decides every outcome.
